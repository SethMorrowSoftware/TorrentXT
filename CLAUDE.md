# CLAUDE.md

Guidance for Claude Code in the TorrentXT member of the xtalk-suite monorepo (`torrentxt/`).
The code and `docs/api-reference.md` win any disagreement. Code comments citing "plan section
N" mean the retired design brief, TorrentXT-IMPLEMENTATION-PLAN.md under docs/archive in git
history (last changed in bf9b158); what still matters from it is in `docs/architecture.md`.

## What this is

**TorrentXT** opens the full BitTorrent protocol to OpenXTalk (OXT) and the xTalk family (also
LiveCode 9.6.3+): add, control, seed and inspect torrents (DHT, PEX, magnets/metadata, uTP,
encryption, HTTP+UDP trackers, webseeds, v1+v2) from script. Layers: libtorrent-rasterbar
(BSD-3) + Boost.Asio own the network and disk threads -> `src/torrent_shim.cpp` builds
`torrentxt.{so,dll,dylib}` exporting `btx_*` -> `src/torrent.lcb` is library
`org.openxtalk.library.torrent` with the public `bt*` handlers ->
`examples/torrent-helpers.livecodescript` (stack "torrentHelpers") is the poll dispatcher.
85 public handlers over 78 bindings, at **ABI 11** (`BTX_ABI_VERSION` in `src/btx_abi.h`
equals `kABIVersion` in `src/torrent.lcb`).

- `src/` - shim, binding, the header-only contracts (`btx_abi.h`, `btx_record.h`,
  `btx_handle_table.h`), `torrentxt.map` (version script), `code/` (libraries + `MANIFEST.sha256`).
- `tests/` - ctest (`record_handle_test.cpp`, `torrent_smoke_test.cpp`,
  `rp1_integration_test.cpp`), the `*golden*.py` suites, and the engine harness
  `torrent-selftest.livecodescript` (folded into the suite paste).
- `examples/` - the helper plus four demos: quickshare, client, dht-channels, rp1-chat.
- `tools/` - `run-gates.sh`, `check-livecodescript.py`, `check-record-registry.py`,
  `package-extension.py`. `docs/` - getting-started, api-reference, architecture, building.
- `.github/workflows/` - GENERATED by the suite's `tools/sync-member-workflows.py`.

The library ships bundled at `src/code/<arch>-<platform>/torrentxt.{so,dll,dylib}` (bare
token, no `lib` prefix; platform-ids exactly `x86_64-linux`, `x86-linux`, `x86_64-win32`,
`x86-win32`, `universal-mac`: architecture first, `-win32` for both bitnesses), and the engine
resolves `c:torrentxt>` through `the revLibraryMapping` (no loose library, `sudo`, `/usr/lib`,
`LD_LIBRARY_PATH` or rename). The C ABI is engine-agnostic: the recorded rqbit (Rust cdylib)
fallback would reproduce the same `btx_*` surface and leave the LCB layer untouched.

## The rules that make this safe

1. **Never call an LCB handler from a libtorrent thread.** Inbound events ride libtorrent's
   alert queue, which `btPoll` poll-drains through `btx_pop_alerts` on a timer. No callback
   ever runs script; only the engine's main thread calls into LCB.
2. **The exception firewall.** libtorrent throws, and an exception crossing `extern "C"` takes
   the engine down. Every `btx_*` entry is `try { ... } catch (...) { btx_set_error(...);
   return <error>; }` (the `BTX_GUARD_*` macros); a smoke test forces a throw and asserts it
   surfaces as an error code.
3. **Payload never crosses the FFI into script.** Piece data moves engine <-> disk on
   libtorrent's threads; only small status records and events cross.

## Working rules

4. A `.lcb` change is only "done" once `tools/check-livecodescript.py` passes, and its runtime
   stays "verified statically; needs an OXT pass" until an engine runs it.
5. **A shim change is only done once torrent_smoke_test.cpp passes under ASan/UBSan** (gcc;
   clang's ASan runtime is not installed here). An ABI change bumps `BTX_ABI_VERSION` and
   `kABIVersion` together; `_checkABI()`, called only from `btStartSession`, throws on skew.
6. **A native-library change is only done once package-extension.py has refreshed the
   committed binary in the same change**, with its `src/code/MANIFEST.sha256` line
   (`run-gates.sh` fails an unlisted or changed blob). The canonical path is a suite
   `release-binaries.yml` dispatch, whose `install-release-binaries.py` does both. CI lanes
   never commit a binary.
7. **Adding a handler, in order:** the `btx_*` function (validate the handle, `try/catch(...)`,
   fill caller buffers, 64-bit values as strings) -> a private foreign handler plus a public
   `bt*` wrapper -> the symbol in `CMakeLists.txt`'s export list (it generates `torrentxt.def`
   for MSVC) -> an ABI bump if needed -> a smoke-test assertion -> binaries + manifest.
8. Test the binding, not BitTorrent: piece hashing, choking and wire correctness are
   libtorrent's job.
9. Naming: `t`/`p`/`s`/`k` prefixes; public `btPascalCase`; C ABI `btx_snake_case`, a
   permanent prefix (the `.lcb` `binds to "c:torrentxt>btx_..."` strings reference it). Comment
   the why, densely. Per-task branch and a draft PR; never push to `main` unasked.
10. Engine behaviour goes in the suite's `docs/OXT-ENGINE-NOTES.md`
    (https://github.com/SethMorrowSoftware/xtalk-suite/blob/main/docs/OXT-ENGINE-NOTES.md);
    member-specific traps stay here.

## FFI / C-ABI conventions

`docs/architecture.md` has the detail; the rules are:

- Handles are positive 32-bit ints, generation-tagged, `0` invalid; a stale handle is a
  harmless no-op. Two tables (sessions, torrents), plus libtorrent's `handle.is_valid()`.
- Reals cross as `double`, booleans as `int` 0/1. No 64-bit foreign int: 64-bit values and
  info-hashes cross as decimal/hex `ZStringUTF8`, like every short string.
- **An LCB `Data` does NOT auto-bridge to a `Pointer`**: it marshals as an opaque `MCDataRef`,
  and passing one where a `Pointer` is declared raises `expected type pointer`. Out buffers are
  a `<builtin>` `MCMemoryAllocate` block (the shim returns bytes written or `-needed`; the
  binding copies back with `MCDataCreateWithBytes`); in buffers pass `MCDataGetBytePtr` plus
  the length. `<builtin>` handlers bind by NAME, so they carry no leading underscore.
- Never return a library-owned `const char*` of unknown lifetime; return `""`, never `NULL`.
- Record schema: `[count:u16]` then `[fieldId:u8][type:u8][len:u16][bytes]`, all framing
  BIG-endian (never "fix" it). One registry in `btx_record.h`, append-only, an ABI bump per
  field; pinned by `record_golden_test.py`, `record_handle_test.cpp`, `check-record-registry.py`.
- The drain never drops a record at the shim: an oversized one is stashed and emitted next
  call (ShowControl's MIDI rule). The queues upstream of it do have caps (gotcha 6).

## Gotchas and traps

C++ engine (the shim cites these by number):

1. Exceptions must never cross `extern "C"` (rule 2).
2. **No deterministic LCB unload hook.** `btStopSession` is mandatory (e.g. in `closeStack`):
   pause -> request and drain resume data -> `abort()` -> destroy -> drop the proxy (its dtor
   joins the threads). It is idempotent, and the shim refuses a second concurrent session with
   `BTX_ERR_SESSION_LIVE` (-4): ONE session per OXT process. Close other session-holding stacks
   and restart OXT before each paste (runbook trap 5.1.1: on 2026-08-10 a leftover session made
   the probe SKIP TorrentXT and held UDP 27196).
3. Boost is the build risk, not the binding: include its and libtorrent's headers with
   `-isystem`, and pin versions.
4. **`src/torrentxt.map` must NOT apply when `TORRENTXT_USE_SYSTEM_LIBTORRENT=ON`.** It keeps
   the statically linked libtorrent/Boost/OpenSSL symbols and, with `-static-libstdc++
   -static-libgcc`, the private C++ runtime out of the export table (`-fvisibility=hidden`
   cannot: archive objects carry their own visibility; measured, a trivial .so exports 781
   symbols, 16 of them `__cxa_*`, and the script cuts that to 1). On the system path
   `libtorrent-rasterbar.so` is a second C++ DSO on `libstdc++.so.6`, and the firewall would
   catch its throws on a different `__cxa_*`. Symptom (2026-08-26): `torrent_smoke_test`
   aborted with NO output in the ASan lane. The CMake gate prints when it skips the script; the
   smoke test announces each section on unbuffered stdout. datachannelxt has the same guard.
5. **libtorrent 2.1 removed APIs; the shim supports both generations** behind
   `#if LIBTORRENT_VERSION_NUM >= 20100` (vcpkg rolled Windows to 2.1 on 2026-08-23):
   `file_storage`/`add_files` -> `std::vector<create_file_entry>` + `lt::list_files`;
   `peer_info::ip` -> `remote_endpoint()`; `torrent_info::files()` -> `layout()`; the
   from-buffer `torrent_info` ec-constructor -> `lt::load_torrent_buffer` (present from 2.0.10,
   one spelling for both; its throwing overload sits in a local try, so a malformed `.torrent`
   still reports "invalid .torrent"). **Version conditionals live at FILE scope only**
   (`btx_build_torrent_blob`, `btx_peer_endpoint`, `btx_file_layout`): a directive inside a
   `BTX_GUARD_*` macro argument is ill-formed, and MSVC refuses it (C2121) where gcc accepts it.
   Verify against 2.1 by compiling the WHOLE shim against the RC_2_1 headers
   (`g++ -fsyntax-only -DTORRENT_ABI_VERSION=4`), and read the whole failed log: a 60-line tail
   hid three more removals. If the FetchContent pin or apt/brew roll to 2.1, run the smoke
   test's create-torrent leg first.
6. **The poll interval is a latency/CPU knob only WITHIN the queue caps.** libtorrent's alert
   queue (`alert_queue_size`, 2000 by default in libtorrent 2.0 - settings_pack.cpp, 2.0.10;
   this line and the shim comment in `btx_pop_alerts` said 1000, which was 1.2's, corrected
   here 2026-09-24, the shim comment at its next native change) DROPS alerts when it fills between drains;
   since 2026-09-10 `btx_pop_alerts` counts `alerts_dropped_alert` (its bitset names dropped
   TYPES, not a count). The rp1 inbound queue (fed from network threads; `btx_rp1_poll` drains
   at most `kDrainCap`, 65536 bytes, per call: about 262 KB/s at 250 ms) was UNBOUNDED until
   2026-09-08, a remote memory exhaustion needing no protocol violation. It now sheds the
   NEWEST event past `kRp1MaxQueueEvents` (65536) or `kRp1MaxQueueBytes` (32 MiB), counting
   the shed (datachannelxt's policy, copied on purpose); every producer goes through
   `enqueue_locked`, and `drain` releases budget with the same `cost()` enqueue charged. Both
   overflows are reported through `btLastError()` at the end of the drain ("rp1: N inbound
   event(s) shed - ..." and "alerts: libtorrent dropped alerts of N type(s) since the last
   drain - ..."; full text in `docs/api-reference.md`). That channel is sticky (a clean drain
   never clears it), so the helper stack clears it before each drain and reads it after, and
   hands a non-empty read to the target as a `torrentPollWarning` event (since 2026-09-24;
   verified statically; needs an OXT pass). Alert codes (`A_RP1_QUEUE_OVERFLOW` + an alerts-dropped code)
   wait for **ABI 12**: the suite's `check-binary-freshness.py` decodes `btx_abi_version()`
   from every committed library, so the bump must land with a release dispatch of all five.
   Pinned since 2026-09-24: `tests/rp1_queue_test.cpp` holds both rp1 caps (it compiles the
   shim source in: nothing exported can feed that queue, and a test hook is a shim change);
   the smoke test forces a real libtorrent overflow (`alert_queue_size` = 1) and requires the
   report, then silence once nothing drops. Its first draft lowered the limit under a queue
   already holding four alerts, and libtorrent dropped the REPORT of the drop too:
   `alerts_dropped_alert` is admitted only while `queue.size() / 4 < limit`.
7. **BEP44 caps the BENCODED value at 1000 bytes.** `btx_dht_put_immutable` and
   `btx_dht_put_mutable` bencode internally, so they cap RAW input at `kBep44MaxRawValue` = 996
   ("996:" is 4 bytes; fixed 2026-09-08). `btx_dht_put_signed` (value emitted verbatim as
   `preformatted_type`) and `btx_dht_bep44_signbuf` (value appended after `1:v`) take
   ALREADY-BENCODED bytes, so their 1000 cap is correct and must stay. Every node refuses an
   over-size put silently; riptide's `kRsMaxRecord` had the same bug and is fixed too. Pinned
   at the boundaries since 2026-09-24 (the old row refused only 1001, which the pre-fix cap
   refused too): 996 in / 997 out in the smoke test and the script harness, 1000 in / 1001
   out for the two already-bencoded paths.

**FOUND 2026-09-24: libtorrent 2.0.x accepts a non-hex 40-character btih.** Its
`magnet_uri.cpp` ignores `from_hex`'s result for a 40-character `urn:btih:` (2.0.10, 2.0.11;
2.1.1 checks it), so `btx_add_magnet` ADDS a torrent for whatever `from_hex` wrote before the
bad digit: "btxtor1:..." becomes info-hash b000...0 and announces for nothing. The Linux and
mac binaries link 2.0.11, the Windows DLLs 2.1.1, so one string is refused on Windows only.
Reachable through any 40-character non-hex code in Quick Share's bare-hash path (`qsGetFile`
checks the length, not the hex) and through a pre-Model-C Quick Share fed a `BTXTOR1:` code cut
to exactly 40 characters (ONIONXT-INTEGRATION-PLAN register #17). The fix is a hex check in
`btx_add_magnet` before `parse_magnet_uri`, a native change that waits for a release dispatch;
`test_pre_model_c_btxtor1_magnet` pins today's answer per libtorrent version.

The 2026-09-24 native rows in gotchas 6 and 7 and this finding are native results: gcc
ASan/UBSan on Linux x86_64 against apt libtorrent 2.0.10, all four ctests green, each fix's
rows mutation-checked against a deliberately broken shim that was then restored. None is an
engine result; the harness's 996/997 rows are verified statically; needs an OXT pass.

Script layer:

8. No smart or curly quotes anywhere, comments included (suite engine note 1.4).
9. A prefixed name whose full spelling is a reserved token IS the token: `tExt` is `text`
   (engine note 1.5); the checker flags it, so use a stem like `tSuffix`.
10. Constants are literal and declared before first use (engine notes 1.2, 1.3).
11. In `.lcb`, `unsafe ... end unsafe` around every foreign call and declarations at the TOP of
    the handler (engine notes section 4); mid-handler `local` is legal in `.livecodescript`.
12. Commands report via `the result`, functions return a value (`btAddMagnet` is a command).
13. `itemDelimiter` / `lineDelimiter` are global: set them right before use (engine note 2.3).
14. Event handlers take ONE event array (`dispatch tName to sPollTarget with tEvent`): write
    `on pieceFinished pEvent` and read `pEvent["piece"]`.

**Performance playbook.** OXT runs script, the FFI and rendering on ONE thread; the costs, in
order, are interpreter ops, FFI round-trips and property-set redraws. One FFI round-trip per
poll (the batched drain, the one-call status snapshot); reuse the persistent buffers
(`sDrainPtr`, `sStatusPtr`, `sScratchPtr`); one clock read per pass; UI text at <= ~4 Hz and
only on change, never per `pieceFinished`; a cadence at which neither queue fills (gotcha 6).

## Example demos: SodiumXT dependency (the channels + quickshare demos)

`torrent-dht-channels` and `torrent-quickshare` do their optional encryption through
**SodiumXT** (`org.openxtalk.library.sodium`), not OXT's `encrypt using "aes-256-cbc"`:
Argon2id `sxPwHash` derives the key, `sxSecretBox` (XSalsa20-Poly1305) seals the channel feed,
`sxEncryptFile` (secretstream) seals files. The channels demo salts the KDF with the channel's
public key; Quick Share uses a random salt carried in the share code.

- Each demo probes SodiumXT once (a guarded `sxSecretBox` round trip in a `try`) into
  `sCanEncrypt`; without it the passphrase features fail closed with an "install
  org.openxtalk.library.sodium" message and everything else works. Never call `sx*` outside
  an `sCanEncrypt` guard or a `try`.
- **The probes run BEFORE `btStartSession`.** A session failure exits the start handler, so
  probes below it left `sCanEncrypt` empty and every caption claimed "needs SodiumXT" while
  another stack held the session. nocloud fixed this 2026-08-24; ported to both demos
  2026-08-27 with nocloud's `sEncryptWhy` / `*EncryptAdvice` (an ABI skew names itself;
  "reinstall" is not "install") and a capability line on the session-failure path. Verified
  statically; needs an OXT pass.
- The old AES format does not open (feed marker `BTXENC1:` -> `BTXENC2:`, accepted on
  purpose). The KDF parameters (opslimit `"2"` + `sxPwMemInteractive()`) must match on both
  ends; change both sides and bump the on-wire format together.
- The dependency is SodiumXT; the wrong name "cryptoXT" was purged 2026-08-17/19, and
  `tests/bep44_golden_test.py` lines 18 and 31 keep it on purpose as dated vector provenance.
  Lesson: a completion claim is about the whole tree, so measure the tree, not the diff.

## Build and gates

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DTORRENTXT_BUILD_TESTS=ON
cmake --build build --config Release
ctest --test-dir build --output-on-failure   # record_handle_test, torrent_smoke_test, rp1_integration_test, rp1_queue_test
bash tools/run-gates.sh                      # checker, tests/*golden*.py, the Model C execution gate, record registry, MANIFEST
g++ -std=c++17 -Wall -Wextra -fsanitize=address,undefined -fno-sanitize-recover=all \
  -isystem <libtorrent-include> -isystem <boost-include> \
  src/torrent_shim.cpp tests/torrent_smoke_test.cpp <link libtorrent + boost> -o /tmp/tt && /tmp/tt
```

FetchContent pins libtorrent `GIT_TAG v2.0.11` and needs Boost >= 1.70; the output is ONE
shared library named with the bare token (`PREFIX ""`, `OUTPUT_NAME torrentxt`). Keep the shim
warning-clean (`/W3` on MSVC). OXT cannot compile `.lcb` or `.livecodescript` headlessly, but
since 2026-09-24 `tools/check-script-vectors.py` RUNS the demos' Model C receive paths (the
BTXO receivers, `qsKeyOpensVerifier`, `qsReceiveOnion`'s parse, the Channels feed seal)
through riptide's runner against `tests/onion_frame_golden.py`'s mirrors and the committed
SodiumXT; it settles logic, not parser behaviour, so it upgrades no honesty label. Its
siblings are riptide, nostrxt and sodiumxt. `docs/building.md` has the options, floors and CI.
